ระบบ Artifact SFTP v1.0 ทำงานอย่างไร

💡 ข้อสังเกตก่อนอ่าน: v1.0 คือ กติกาและเครื่องมือ ที่เพิ่งประกาศใช้ (เผยแพร่ถึง v1.0.3) — บนเครื่องนี้ยังไม่มี artifact ใดถูกอัปโหลดขึ้น Cloudflare R2 เพราะยังไม่มีใคร provision bucket ระบบจึงใช้ profile SFTP เดิมต่อไป จนกว่าเจ้าของจะตั้งค่า R2

สรุป 3 บรรทัด

  • ประตูเดียว: AI Agent ขึ้นของผ่านเครื่องมือ artifact_sftp.publish เท่านั้น — เหมือนเคาน์เตอร์ส่งพัสดุที่มีหน้าเดียว ตรวจของก่อนรับเสมอ
  • ด่านตรวจซ้อน: ก่อนของขึ้น host ระบบตรวจคุณภาพไฟล์ แสกนของต้องห้าม กันเขียนทับของผู้อื่น และยืนยันว่าของ private ถูกปิดตายจริง
  • ที่อยู่ใหม่แบบมีโครง: v1 จัดเก็บตาม /{project}/{private|public}/{slug}/ แทนการเรียงตามชื่อ AI tool

แผนผังการไหล

5 ขั้นตอนเมื่อ “publish” หนึ่งครั้ง

  1. Agent ส่งไฟล์ HTML เข้า artifact_sftp.publish — ประตู MCP เดียวที่ระบบอนุญาต (สั่งตรงผ่าน shell ถือเป็นการ bypass และถูกปฏิเสธ)
  2. artifact-audit ให้คะแนนไฟล์ 5 มิติ — ถ้าเจอปัญหาร้ายแรง (🔴 BLOCK) เช่น secret หรือ active content จากเว็บอื่น การเผยแพร่หยุดทันที
  3. publisher สแกนซ้ำในตัว (secret + external active content โดย parse HTML จริง) แล้วตรวจ custody — ถ้า slug นี้มีของอยู่แล้ว ต้องพิสูจน์ว่าเรามีสำเนาตรงกัน จึงจะอัปเดตได้
  4. ก่อนขึ้น private (v1) ระบบลองเข้า URL แบบไม่ติดตั้งตัวตน — ต้องโดน Cloudflare Access ต้อน (302/401/403) ถ้าเปิดอ่านได้ฟรี (200) ระบบหยุดและไม่อัปโหลดอะไรเลย
  5. ของถูกเก็บสำเนาในเครื่องก่อน แล้วอัปโหลดตาม profile — Agent ได้ทั้ง URL และพาธไฟล์สำรองในเครื่องกลับไปตรวจสอบ

อะไรเปลี่ยนใน v1.0

  • ที่อยู่จัดตามโครงการ: URL ใหม่เป็น /{project}/{visibility}/{slug}/ — โปรเจกต์คือ namespace ที่เจ้าของตั้ง ไม่ผูกกับชื่อ AI tool ที่สร้างไฟล์
  • Cloudflare R2 เป็นค่าตั้งต้นของโปรไฟล์ใหม่: กด setup แล้วระบบชี้ R2 เป็นทางที่แนะนำ พร้อมเช็กลิสต์ (bucket ปิดหูรับสาธารณะ, token เฉพาะงาน, Access ต้องตั้งก่อนผูกโดเมน) — แต่ระบบไม่สร้างของพวกนี้ให้เอง และไม่เคยสลับไป backend อื่นเงียบ ๆ
  • โปรไฟล์เดิมไม่ถูกยุบ: config เก่าที่ไม่มี marker ยังทำงานรูปแบบเดิม 100% — การอัปเกรดตัว plugin ไม่มีวันย้ายของใคร
